# Lessons（同じミスを繰り返さないための記録）

## C++ソース(.cpp/.h)に追加するコメントは英語で書く
- **状況**: `DXRPipeline.cpp` に「加速構造」等の漢字コメントを追加したらビルドエラー（`currentChecksum`が定義されていない識別子、C2065）。
- **原因**: ファイルはUTF-8だが、MSVCがコードページ932(Shift-JIS)として解釈する。「構」(Shift-JIS 0x8D5C)など**2バイト目が0x5C(`\`)になる漢字**が行末付近にあると、行継続扱いで次行のコード（`uint64_t currentChecksum = ...`）がコメントに巻き込まれて消える。`warning C4819`（コードページ932で表示できない文字）が前兆サイン。
- **対策**: **ネイティブC++ソース(.cpp/.h)に新規追加するコメントは英語で書く**。既存の日本語コメントは壊れていなければ触らない。C#(.cs)やドキュメントは日本語でOK（UTF-8として正しく扱われる）。
- **適用範囲**: `src/RayTraceVS.DXEngine/` `src/RayTraceVS.Interop/` のネイティブコードを編集する全タスク。

## リファクタリングは検証基盤を先に作る
- **状況**: RayTraceVSのリファクタリングで、出力同一性を検証する手段（テスト・ヘッドレス出力）が当初なかった。
- **対策**: Phase 0でヘッドレスレンダリング＋ピクセル比較を実装してから本体に着手。各変更後に `.\tools\verify_render.ps1` で完全一致を確認。[[verification-workflow]]参照（メモリ）。
- **効果**: C#層は出力ピクセル完全一致、C++最適化も同一性を客観確認できた。

## シェーダーキャッシュ(.cso)の世代が変わると出力ピクセルが変わる
- **状況**: Releaseビルドを実行したら、それ以降のDebug検証が「差分1.8%」でNGになった。コード変更は無関係だった。
- **原因**: シェーダーキャッシュは `src\Shader\Cache\`（作業ディレクトリ相対）を**全ビルド構成で共有**しており、Releaseビルドが別フラグでコンパイルした.csoで上書きする。また、GPUのadapterLUIDは再起動ごとに変わるため、セッション初回ビルドでも全シェーダーが再コンパイルされる。再コンパイルされたシェーダーバイナリは（同一ソースでも）演算順序が変わり、レイトレ出力が微妙に変わる。
- **切り分け**: 差分のピクセル数・パターンが「過去のシェーダー世代差のNG」と一致していたら世代差を疑う。決定打は**同一.csoを共有させた新旧コードバイナリの出力直接比較**（完全一致すればコードは無罪）。
- **対策**: (1) 検証セッション中はReleaseビルドを挟まない（最後にまとめる）。(2) .cso再生成が起きたらベースラインも再生成（変更前コードの出力から）。(3) ベースライン画像は「シーン＋シェーダー世代」に紐づくものと理解する。

## HLSL変更の無害性は「プリプロセス比較＋同一セッション再コンパイル比較」で証明できる
- **状況**: 第3弾Step 5でHLSL構造体定義をSharedTypes.hへ移動する際、変更の無害性を検証する必要があった。
- **実験で確認した事実**: (1) .csoは`-Zi -Qembed_debug`のデバッグ情報埋め込みのため、**ソース無変更でも再コンパイルするとバイナリが変わる**（13個中12個不一致）。(2) 別世代の.csoとは出力ピクセルも変わる（差分1.8%パターン）。(3) しかし**同一セッション内の再コンパイルは出力レベルで決定的**（2回連続再コンパイルでピクセル完全一致）。
- **検証手順**: ①変更前に `dxc -P`（プリプロセスのみ）で全シェーダーの展開結果を保存 → ②ベースラインを現世代.csoで再生成 → ③HLSL変更 → ④プリプロセス出力を再取得し正規化diff（意味的同一性の証明）→ ⑤再コンパイル後にverify_render（同一セッションなら差分が出たら自分の変更のせいと断定できる）。
- **注意**: プリプロセス比較で構造体定義の「出現位置の移動」は順序込み比較だと差分になるが、使用前に定義されていれば意味は同一（集合比較＋行数一致＋差分内容の目視で判断）。

## ベースライン画像はシーンファイル変更で陳腐化する
- **状況**: 最適化第2弾の初回検証で「検証NG（差分1.8%）」。実際はコード変更が原因ではなく、前回セッション終了間際に sample_scene.rtvs が変更され（5/24 5:33）、ベースライン（5/24 4:02生成）が古くなっていた。
- **切り分け手順**: (1) ベースラインとシーンファイルのタイムスタンプを比較 → シーンの方が新しければ陳腐化を疑う。(2) コード変更だけを `git stash push -- <ファイル>` で退避し、旧コード＋現シーンの出力と新コード＋現シーンの出力を `--compare` で直接比較 → 完全一致ならコード変更は無罪と証明できる。
- **対策**: 検証NGが出たら、自分の変更を疑う前にまずベースラインの鮮度を確認する。ベースライン再生成は「変更前コード」の出力から行う。
